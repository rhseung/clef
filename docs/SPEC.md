# 음악 프로그래밍 언어 컴파일러 설계서

Nov 16, 2026 @류현승

## 개요

이 프로젝트는 악보를 코드로 작성하는 작은 언어와, 그 코드를 컴파일 단계에서 검사해 MIDI 이벤트에 대응하는 중간 표현으로 바꾸는 컴파일러를 만든다. 언어 이름은 Clef이다.

### 목표와 범위

- 소스 언어는 음악을 표현하는 DSL이다. 음(Note), 음정(Interval), 구절(Phrase)을 값으로 다룬다.
- 타깃은 틱 기반 이벤트 중간 표현이다. 이벤트 하나는 (tick, channel, pitch, duration)이고, Standard MIDI File의 음 이벤트와 일대일로 대응한다.
- 컴파일러는 렉서, 파서, AST, 의미 분석, 중간 표현 생성, 최적화까지 구현한다. 기계어 생성은 하지 않는다.
- 중간 표현을 SMF 파일로 쓰는 출력기는 선택 사항이다.
- 구현 언어는 TypeScript이다. 이 문서는 언어에 의존하지 않는 형태로 자료구조를 기술한다.

### 핵심 아이디어

악보의 오류를 연주 전에 컴파일러가 증명한다는 점이 이 언어의 특징이다. 컴파일러가 검사하는 항목은 다음과 같다.

- 연산자의 타입 규칙(음 + 음정은 음, 음 + 음은 오류)
- 조성에 따라 의미가 달라지는 온음계 이조(C장조의 C4 + 2d는 E4, D4 + 2d는 F4)
- 정확한 유리수 시간 계산(마디 길이 검사, 480 PPQ 틱으로 표현할 수 없는 길이 거부)
- 악기 음역과 채널 한도
- 컴파일 시점에 계산 가능한지 여부(재귀 금지, 상수 반복 횟수)
- 붙임줄이 같은 음높이의 다음 음으로 이어지는지 여부

## 실행 규약

모든 팀이 같은 명령을 쓴다. 채점자가 직접 만든 파일을 현장에서 주므로 이 규약이 다른 절보다 우선한다.

```
./run.sh --phase lex   myfile.src
./run.sh --phase parse myfile.src
./run.sh --phase sema  myfile.src
./run.sh --phase ir    myfile.src
```

| 상황                                              | 종료 코드 | 출력                                                                         |
| ------------------------------------------------- | --------- | ---------------------------------------------------------------------------- |
| 올바른 프로그램(경고만 있어도)                    | 0         | 표준 출력에 단계의 결과, 표준 에러에 경고                                    |
| 잘못된 프로그램, 읽을 수 없는 파일, 잘못된 사용법 | 2         | 표준 에러에 진단. 표준 출력에는 아무것도 쓰지 않는다                         |
| 컴파일러 자체의 고장                              | 1         | `clef: internal compiler error: <메시지>` 한 줄. 스택 트레이스를 내지 않는다 |

- 결과와 진단 말고는 아무것도 출력하지 않는다.
- 파일 확장자는 검사하지 않는다. `.src`든 `.clef`든 읽는다.
- 빈 파일, 임의의 바이트, 아주 깊은 중첩에도 종료 코드 1이 나오면 안 된다.

| `--phase` | 실행하는 단계 | 성공할 때의 출력                                                              |
| --------- | ------------- | ----------------------------------------------------------------------------- |
| `lex`     | 1             | 토큰 목록                                                                     |
| `parse`   | 1 ~ 2         | 파스 트리                                                                     |
| `sema`    | 1 ~ 7         | 이름과 타입 목록(4단계의 `typed`). 6단계의 오류(E3xx, E4xx)도 여기에서 나온다 |
| `ir`      | 1 ~ 8         | LIR. 헤더 줄을 포함한다                                                       |

`sema`가 평가 단계까지 도는 이유는 마디 길이, 음역, 붙임줄 같은 의미 오류를 평가기가 찾기 때문이다.

시연용 선택 옵션은 `--emit ast|ast-opt|hir|hir-opt`(`--phase` 대신 내부 단계를 본다), `-O0`, `-o <출력.mid>`이다.

## 어휘 규칙

렉서는 소스 문자열을 토큰 열로 바꾼다. 이 언어에서 렉서의 핵심 난점은 음 토큰(`C4`)과 이름 토큰(`c4`)을 구분하는 것이다.

### 토큰 종류

| 토큰            | 형태                                                                                       | 예                      | 토큰 값                  |
| --------------- | ------------------------------------------------------------------------------------------ | ----------------------- | ------------------------ |
| NOTE            | A부터 G중 한 글자, 임시표(# 또는 b)는 선택, 숫자 한 자리                                   | `C4`, `C#4`, `Bb3`      | (음이름, 임시표, 옥타브) |
| PITCHCLASS      | A부터 G중 한 글자, 임시표(# 또는 b)는 선택, 뒤에 숫자가 없는 경우                          | `C`, `F#`, `Bb`         | (음이름, 임시표)         |
| IDENT           | `[a-z][a-zA-Z0-9_]*`                                                                       | `m1`, `c4`, `bass_line` | 문자열                   |
| INT             | `[0-9]+`                                                                                   | `4`, `480`              | 정수                     |
| INTERVAL        | INT 바로 뒤에 `d` 또는 `st`                                                                | `2d`, `3st`             | (크기, 종류)             |
| REST            | `_`                                                                                        | `_`                     | 없음                     |
| BAR             | `\|`                                                                                       | `\|`                    | 없음                     |
| TIE             | `~`                                                                                        | `~`                     | 없음                     |
| 연산자와 구두점 | `=` `+` `-` `*` `&` `:` `/` `(` `)` `[` `]` `,`                                            | 없음                    | 없음                     |
| 키워드          | `time` `key` `tempo` `unit` `track` `def` `major` `minor` `Note` `Interval` `Phrase` `Int` | 없음                    | 없음                     |
| NEWLINE, EOF    | 줄바꿈과 입력의 끝                                                                         | 없음                    | 없음                     |

INTERVAL의 `d`는 온음계 계단(diatonic step) 수이고 `st`는 반음(semitone) 수이다. `2d`는 조성의 음계에서 두 계단 위로 이동하는 음정이다.

### 구분 규칙

1. 대문자 A부터 G로 시작하면 음 후보로 본다. 이름 다음에 임시표(`#` 또는 `b`)가 올 수 있고, 그 다음에 숫자 한 자리가 오면 NOTE이다. 숫자가 없으면 PITCHCLASS이다. 숫자가 두 자리 이상이거나 뒤에 식별자 문자가 붙으면 E002이다.
2. 소문자로 시작하는 단어는 언제나 IDENT이다. `c4`는 음이 아니라 이름이다. 키워드는 IDENT로 쓸 수 없다.
3. PITCHCLASS는 `key` 헤더에서만 유효하다. 식 안에 나오면 파서가 E002를 보고한다.
4. `#`는 음 이름 바로 뒤에서만 올림표로 쓴다. 그 외의 `#`는 E001이다. 주석은 `#`가 아니라 `//`로 쓴다.
5. INT 바로 뒤에 공백 없이 `d` 또는 `st`가 오면 INTERVAL이다. 그 뒤에 식별자 문자가 더 이어지거나 다른 문자가 오면 E003이다.
6. `-`는 항상 MINUS 토큰이다. 음수 리터럴은 없다. 반대 방향 이조는 `m1 - 2d`로 쓴다.
7. `/`와 `:`는 문맥과 상관없이 SLASH, COLON 토큰이다. `time 4/4`의 박자표와 `C4:3/2`의 길이 표기는 파서가 구분한다.
8. 공백과 탭은 토큰을 나눠 주지만 토큰 사이에 연결 연산이 숨어 있다. IDENT 두 개는 반드시 공백으로 띄어 써야 한다. `m1m1`은 하나의 IDENT이다.
9. `//`부터 줄 끝까지는 주석이고 토큰을 만들지 않는다.
10. NEWLINE은 문장의 끝을 뜻한다. `(` 또는 `[` 안에서는 NEWLINE을 만들지 않고, 연속된 줄바꿈은 하나로 합친다. 파일 맨 앞의 줄바꿈과 NEWLINE 바로 뒤의 줄바꿈은 건너뛴다. 입력의 마지막이 NEWLINE이 아니면 EOF 앞에 NEWLINE을 하나 넣는다. 이 NEWLINE은 괄호가 열려 있어도 낸다. 토큰이 하나도 없는 입력(빈 파일, 공백과 주석뿐인 파일)은 E005이다.
11. 위치는 줄과 열 모두 1부터 세고, 열은 문자 단위로 센다. 탭도 1열이다.
12. 정수 리터럴은 0 이상 2^53 - 1 이하이다. 이보다 크면 E004이고 그 토큰은 버린다.
13. 파일 맨 앞의 BOM은 버리고, `\r`은 공백으로 읽는다. 그래서 CRLF 파일도 같은 결과를 낸다. E001 메시지에서 출력할 수 없는 문자는 `U+0000` 꼴로 적는다.
14. 어느 규칙에도 맞지 않는 글자, H부터 Z로 시작하는 대문자 단어, `_a`처럼 `_` 뒤에 식별자 문자가 붙은 것은 E001이다. 오류가 난 부분은 버리고 다음 글자부터 계속 읽는다.

### 구분 예시

| 입력          | 토큰                            |
| ------------- | ------------------------------- |
| `C#4`         | NOTE(C, #, 4)                   |
| `c4`          | IDENT(c4)                       |
| `key C minor` | KW_KEY, PITCHCLASS(C), KW_MINOR |
| `m1+2d`       | IDENT(m1), PLUS, INTERVAL(2, d) |
| `E4:2~`       | NOTE(E, 4), COLON, INT(2), TIE  |
| `C10`         | E002, 옥타브는 한 자리          |
| `2x`          | E003, 잘못된 음정 표기          |

### 토큰 자료구조

```
Token {
  kind     : 토큰 종류
  lexeme   : 소스에서 잘라낸 문자열
  value    : 토큰 값 (음이름, 옥타브, 정수 등)
  span     : { line, col, endCol }
}
```

렉서 오류는 E001(알 수 없는 문자), E002(잘못된 음 표기), E003(잘못된 음정 표기), E004(너무 큰 정수 리터럴), E005(빈 프로그램)이다. 렉서는 오류를 보고한 뒤 해당 문자를 건너뛰고 스캔을 계속한다.

## 문법

프로그램은 헤더와 문장으로 구성되고, 식에서 연결 연산이 공백으로 표현된다는 점이 파서의 핵심이다. 파서는 LALR(1) 표를 쓰는 LR 파서로 구현한다. 아래 EBNF를 BNF로 풀어 쓴 문법이 파서 생성기의 입력이다.

### EBNF

```
program   = { header NEWLINE } { stmt NEWLINE } EOF

header    = "time" INT "/" INT
          | "key" PITCHCLASS [ "major" | "minor" ]
          | "tempo" INT
          | "unit" INT "/" INT

stmt      = assign | def | track
assign    = IDENT "=" expr
def       = "def" IDENT "(" [ param { "," param } ] ")" ":" type "=" expr
param     = IDENT ":" type
type      = "Note" | "Interval" | "Phrase" | "Int"
track     = "track" IDENT "=" expr

expr      = par
par       = seq { "&" seq }
seq       = item { item }
item      = BAR | post
post      = atom { ( "+" | "-" ) atom | "*" atom }
atom      = NOTE [ length ] [ TIE ]
          | REST [ length ]
          | IDENT
          | IDENT "(" [ expr { "," expr } ] ")"     // 공백 없이 붙은 괄호만 호출
          | INT
          | INTERVAL
          | "(" expr ")"
          | "[" expr "]" length
length    = ":" ( INT | "/" INT | INT "/" INT )
```

### BNF

EBNF의 반복과 선택을 풀어 쓰고, 한 줄을 한 단위로 보도록 바꾼 문법이다. 대문자는 터미널이고 첫 글자만 대문자인 이름은 논터미널이다. `ε`은 빈 생산이다. 터미널 이름은 토큰 종류와 같고 `CALL_LP`만 예외이다. 이는 아래 파싱 방법에서 설명한다.

```
Program   -> Lines
Lines     -> Lines Line | ε
Line      -> Header NEWLINE | Stmt NEWLINE | ERROR NEWLINE

Header    -> KW_TIME INT SLASH INT
           | KW_KEY PITCHCLASS | KW_KEY PITCHCLASS KW_MAJOR | KW_KEY PITCHCLASS KW_MINOR
           | KW_TEMPO INT
           | KW_UNIT INT SLASH INT

Stmt      -> IDENT EQ Expr
           | KW_DEF IDENT Lp Params RPAREN COLON Type EQ Expr
           | KW_TRACK IDENT EQ Expr
Lp        -> LPAREN | CALL_LP
Params    -> ε | ParamList
ParamList -> Param | ParamList COMMA Param
Param     -> IDENT COLON Type
Type      -> KW_NOTE | KW_INTERVAL | KW_PHRASE | KW_INT

Expr      -> Par
Par       -> Par AMP Seq | Seq
Seq       -> Seq Item | Item
Item      -> BAR | Post
Post      -> Post PLUS Atom | Post MINUS Atom | Post STAR Atom | Atom
Atom      -> NOTE | NOTE Length | NOTE TIE | NOTE Length TIE
           | REST | REST Length
           | IDENT | IDENT CALL_LP Args RPAREN
           | INT | INTERVAL
           | LPAREN Expr RPAREN
           | LBRACKET Expr RBRACKET Length
Length    -> COLON INT | COLON SLASH INT | COLON INT SLASH INT
Args      -> ε | ArgList
ArgList   -> Expr | ArgList COMMA Expr
```

길이의 분자와 분모는 1 이상이어야 한다. `C4:0`과 `C4:/0`은 E012이다. 식의 AST 깊이가 500을 넘으면 E013이다. 두 검사가 없으면 0으로 나누기와 stack overflow가 컴파일러 고장(종료 코드 1)이 된다.

`ERROR`는 렉서가 내지 않는 가상 터미널이고 오류 복구에만 쓴다. 이 문법은 LALR(1)이며 충돌이 없다. 우선순위는 `Par`, `Seq`, `Post`, `Atom`의 계층으로 문법에 들어 있다.

### 연산자 우선순위

높은 것부터 나열한다.

1. 기본 식(atom): 리터럴, 이름, 함수 호출, 괄호, 묶음 `[ ... ]:L`
2. 후위 연산 `+`, `-`, `*`: 왼쪽에서 오른쪽으로 결합하며 연쇄할 수 있다. `m1 + 2d * 2`는 `(m1 + 2d) * 2`이다.
3. 공백 연결(순차 연결): 결합 법칙이 성립하므로 AST에서 하나의 편평한 목록으로 만든다.
4. `&`(병렬): 가장 낮다. `a b & c d`는 `(a b) & (c d)`이다.

이 순서 때문에 `m1 m1+2d`는 `m1`과 `(m1+2d)`를 이은 것으로 해석된다. 괄호 없이 쓸 수 있는 이유는 이조와 반복이 연결보다 우선하기 때문이다.

### 문장 구조 규칙

- 헤더는 모든 문장보다 앞에 와야 한다. 헤더가 문장 뒤에 나오면 파서가 E010(예상하지 못한 토큰)을 보고한다.
- 헤더를 생략하면 기본값을 쓴다. `time 4/4`, `key C major`, `tempo 120`, `unit 1/4`이다. 같은 헤더를 두 번 쓰면 의미 분석이 E102를 보고한다.
- `unit`은 길이 접미사가 곱해지는 기준 길이이다. `C4`의 길이는 `unit`이다.
- 길이 접미사 `:n`은 `unit`의 n배, `:/n`은 1/n배, `:m/n`은 m/n배이다. 예를 들어 `unit 1/4`에서 `C4:3/2`는 점 4분음표이다.
- 한 줄에 문장 하나를 쓴다. 줄바꿈은 `(` 안과 `[` 안에서만 허용한다.
- `track`의 첫 이름은 악기 이름이다. 악기 이름인지는 파서가 아니라 의미 분석이 검사한다(E104).
- BAR는 `item`이지 `atom`이 아니다. 따라서 BAR 바로 뒤에 `+`, `-`, `*`가 올 수 없다.
- `[ ... ]` 묶음은 반드시 뒤에 길이 접미사를 붙여야 한다. 묶음 안에는 BAR를 쓸 수 없다(E306, 의미 분석에서 보고).

### 파싱 방법

LALR(1) 표를 쓰는 LR 파서이다. 표는 위 BNF로 LR(1) 항목 집합을 만들고 core가 같은 상태를 합쳐 얻는다. 생성기를 쓰지 않고 직접 만든다.

- `item`의 시작 토큰 집합은 BAR, NOTE, REST, IDENT, INT, INTERVAL, `(`, `[`이다. `seq`가 끝나는 토큰은 NEWLINE, EOF, `&`, `)`, `]`, `,`이다.
- 함수 호출과 괄호 묶음은 다음 토큰만으로는 구분할 수 없다. `m1 (m1+2d)`는 두 항목의 연결이고 `f(m1)`는 호출이다. 따라서 토큰에 `spaceBefore`(바로 앞에 공백이 있었는지) 필드가 필요하다. 렉서는 두 경우 모두 LPAREN을 낸다. 파서가 터미널을 고를 때 IDENT 바로 뒤에 있고 `spaceBefore`가 없는 `(`만 `CALL_LP`로 바꿔 읽는다.
- 헤더가 문장보다 앞에 와야 한다는 규칙은 문법이 아니라 `Line` 생산을 줄이는 시점의 동작에서 검사한다. 위반하면 E010을 보고하고 그 줄을 버린다. 헤더 구간과 문장 구간을 문법에서 나누면 오류 복구용 생산과 충돌하기 때문이다.
- 오류 복구는 `Line -> ERROR NEWLINE` 생산과 패닉 모드이다. 오류를 만나면 스택에서 `ERROR`를 받을 수 있는 상태까지 팝하고, 입력에서 NEWLINE을 만날 때까지 토큰을 버린 뒤 다음 줄부터 다시 파싱한다.
- E011은 마지막 NEWLINE 또는 EOF에서 구문 오류가 났고 열린 괄호가 남아 있을 때 보고한다. 위치는 가장 안쪽에서 열린 괄호이다. 닫히지 않은 괄호 뒤의 줄은 모두 그 괄호 안으로 들어가므로 그 뒤 문장의 오류는 보고되지 않는다.

### 파싱 예시

| 소스           | 파싱 결과                                             |
| -------------- | ----------------------------------------------------- |
| `m1 m1+2d`     | Seq(m1, Transpose(m1, +2d))                           |
| `m1+2d*2`      | Repeat(Transpose(m1, +2d), 2)                         |
| `a b & c d`    | Par(Seq(a, b), Seq(c, d))                             |
| `f(m1)`        | Call(f, \[m1\])                                       |
| `f (m1)`       | Seq(f, m1), 공백이 있으므로 호출이 아니다             |
| `C4:/2 C4:3/2` | Seq(Note(C4, 1/2), Note(C4, 3/2)), 길이는 unit의 배수 |
| `[C4 D4 E4]:1` | Group(Seq(C4, D4, E4), 1), 전체 길이가 unit의 1배     |

## 타입 체계

타입은 Int, Interval, Note, Phrase 네 가지이고, Note는 Phrase의 부분 타입이다. 모든 표현식의 타입은 소스의 타입 주석 없이 식의 구조로 결정된다. 타입 주석은 함수 매개변수와 반환 타입에서만 쓴다.

### 타입 종류

| 타입     | 의미                              | 값의 예               |
| -------- | --------------------------------- | --------------------- |
| Int      | 정수                              | `4`                   |
| Interval | 이동량 (온음계 계단 또는 반음)    | `2d`, `3st`           |
| Note     | 음 하나 (높이, 길이, 붙임줄 여부) | `C4`, `E4:2`          |
| Phrase   | 음과 쉼표의 시간 배열             | `C4 E4 G4`, `_`, `m1` |

쉼표 `_`는 Phrase이다. 묶음 `[ ... ]:L`의 결과도 Phrase이다.

### 부분 타입

- Note는 Phrase의 부분 타입이다. Phrase가 필요한 자리에 Note를 쓸 수 있다. 반대는 성립하지 않는다.
- Int와 Interval은 서로도, Note와 Phrase와도 호환되지 않는다.

### 연산자별 타입 규칙

| 식                      | 피연산자 타입                       | 결과 타입        | 위반 시 오류 |
| ----------------------- | ----------------------------------- | ---------------- | ------------ |
| `a b` (순차 연결)       | 각 항목이 Phrase 또는 Note          | Phrase           | E201         |
| `a & b` (병렬)          | 둘 다 Phrase 또는 Note              | Phrase           | E201         |
| `e + i`, `e - i` (이조) | (Note, Interval)                    | Note             | E201         |
| `e + i`, `e - i` (이조) | (Phrase, Interval)                  | Phrase           | E201         |
| `e * n` (반복)          | (Phrase 또는 Note, Int)             | Phrase           | E201, E402   |
| `[e]:L` (묶음)          | e가 Phrase 또는 Note                | Phrase           | E201         |
| `f(a1, ...)` (호출)     | 각 인자가 매개변수 타입의 부분 타입 | 선언한 반환 타입 | E203         |
| 이름                    | 정의된 이름                         | 정의의 타입      | E101         |

이조의 오른쪽 피연산자는 Interval이어야 한다. 이 규칙 때문에 `C4 + C4`는 구문 오류가 아니라 타입 오류(E201)로 보고된다. Note를 반복한 `C4 * 2`는 Note가 아니라 Phrase이다.

### 정의와 이름 규칙

- 변수 `name = expr`의 타입은 우변에서 정해진다. 변수는 정의한 줄 이후에서만 보이고, 이름을 다시 정의하면 E103이다. 정의하기 전에 쓰면 E101이다.
- 함수 `def f(p: T1, ...): R = body`는 매개변수 타입과 반환 타입을 반드시 쓴다. 본문의 타입은 R의 부분 타입이어야 한다(위반 시 E204).
- 함수 이름은 파일 전체에서 보인다. 선언 순서와 상관없이 호출할 수 있다. 재귀 여부는 호출 그래프로 별도 검사한다(E401).
- 함수 본문은 함수를 선언한 줄보다 앞에서 정의한 전역 변수만 참조할 수 있다.
- 변수와 함수는 하나의 전역 이름 공간을 쓴다. 둘이 같은 이름이면 E103이다.
- 매개변수는 함수 본문 안에서만 보이고 같은 이름의 전역 변수를 가린다.
- `track name = expr`의 우변은 Phrase(또는 Note)여야 한다. `name`은 악기표에 있는 악기 이름이어야 한다(E104).

### 오류 타입

타입 오류가 난 식의 타입을 오류 타입으로 둔다. 오류 타입을 피연산자로 가지는 식은 새 오류를 내지 않고 오류 타입이 된다. 하나의 원인이 여러 오류로 연쇄해서 나오는 것을 막기 위한 규칙이다.

### 타입 예시

`m1`은 이미 Phrase로 정의되어 있다고 하고, `up`은 `def up(p: Phrase, i: Interval): Phrase = p + i`라고 한다.

| 식          | 타입 또는 오류                                        |
| ----------- | ----------------------------------------------------- |
| `C4`        | Note                                                  |
| `C4 + 2d`   | Note                                                  |
| `C4 E4`     | Phrase                                                |
| `m1 + 2d`   | Phrase                                                |
| `m1 * 2`    | Phrase                                                |
| `C4 + C4`   | E201, (Note, Note)에 대해 `+`가 정의되지 않음         |
| `2d + 2d`   | E201, (Interval, Interval)에 대해 `+`가 정의되지 않음 |
| `C4 2d`     | E201, 순차 연결의 항목이 Interval                     |
| `up(m1)`    | E203, 인자 1개, 필요한 인자 2개                       |
| `up(m1, 3)` | E203, 두 번째 인자가 Int, 필요한 타입은 Interval      |

## 컴파일러 구조

컴파일러는 여덟 단계(선택 단계인 SMF 출력을 더하면 아홉 단계)의 선형 파이프라인이고, 각 단계는 바로 앞 단계의 출력 자료구조만 입력으로 받는다. 단계 사이에 전역 상태를 두지 않으므로 각 단계를 따로 테스트하고 확인할 수 있다.

### 단계별 입출력

| 단계                     | 입력            | 출력                         | 보고하는 오류                        |
| ------------------------ | --------------- | ---------------------------- | ------------------------------------ |
| 1. 렉서                  | 소스 문자열     | Token 목록                   | E001 부터 E005                       |
| 2. 파서                  | Token 목록      | 파스 트리                    | E002, E010 부터 E013                 |
| 3. AST 구축              | 파스 트리       | AST                          | 없음                                 |
| 4. 이름 해석과 타입 검사 | AST             | 타입이 붙은 AST, 심볼 테이블 | E101 부터 E105, E201 부터 E204, E401 |
| 5. AST 최적화            | 타입이 붙은 AST | 최적화된 AST                 | 없음                                 |
| 6. 평가                  | 최적화된 AST    | 고수준 IR (HIR)              | E301 부터 E307, E402, E403           |
| 7. HIR 최적화            | HIR             | 최적화된 HIR                 | 없음                                 |
| 8. 하강                  | HIR             | 저수준 IR (LIR)              | 없음                                 |
| 9. SMF 출력 (선택)       | LIR             | .mid 파일                    | 없음                                 |

오류가 나오면 다음 단계로 넘어가는 규칙은 다음과 같다.

- 렉서와 파서는 오류가 있어도 끝까지 읽으며 여러 오류를 모으고, 오류가 하나라도 있으면 의미 분석으로 넘어가지 않는다.
- 4단계에서 오류가 있으면 6단계(평가)는 실행하지 않는다. 평가는 타입이 맞는 AST를 전제로 하기 때문이다.
- 6단계에서는 정의 하나에 오류가 있어도 다른 정의와 트랙을 계속 평가해 오류를 모두 보고한다.
- 7단계부터는 오류가 없다. 6단계가 끝났을 때 모든 오류가 이미 보고된 상태여야 한다.

### 공통 자료구조

아래 자료구조는 구현 언어에 맞게 레코드, 구조체, 클래스 중 편한 것으로 옮기면 된다.

```
Span        { line, col, endCol }                 // 모든 위치는 1부터 센다
Rational    { num, den }                          // den > 0, 기약 분수로 정규화, 단위는 온음표
Token       { kind, lexeme, value, span, spaceBefore }
Diagnostic  { severity: Error | Warning, code, message, span, help? }
```

### AST

모든 노드는 `span`을 가지고, 4단계 이후에는 표현식 노드가 `type` 필드를 추가로 가진다.

```
Program   { header: Header, stmts: [Stmt] }
Header    { timeNum, timeDen, tonic, mode, tempo, unit: Rational }   // 생략된 값은 기본값으로 채움

Stmt  = Assign { name, expr }
      | Def    { name, params: [(name, type)], ret: type, body: Expr }
      | Track  { instrument, expr }

Expr  = NoteLit     { letter, accidental, octave, lenMul: Rational, tie: bool }
      | RestLit     { lenMul: Rational }
      | IntLit      { value }
      | IntervalLit { amount, kind: Diatonic | Semitone }
      | Var         { name }
      | Call        { name, args: [Expr] }
      | Seq         { items: [Expr | BarMark] }       // 중첩된 Seq는 편평화
      | Par         { left, right }
      | Transpose   { expr, interval: Expr, sign: +1 | -1 }
      | Repeat      { expr, count: Expr }
      | Group       { expr, lenMul: Rational }
```

파스 트리에서 AST로 바꿀 때 괄호 `( )` 노드와 자식이 하나뿐인 중간 규칙 노드를 제거한다. 공백 연결은 편평한 `Seq`로 만든다.

### 심볼 테이블

```
Globals  : name -> { kind: Var | Def, type, span, used: bool }
Def 정보  : params, ret, callees: set of name      // 호출 그래프의 간선
Scope    : 함수 본문 안에서는 매개변수 목록을 전역보다 먼저 찾는다
```

### 모듈 분리

| 모듈     | 책임                                        |
| -------- | ------------------------------------------- |
| lexer    | 문자열에서 Token 목록                       |
| parser   | Token 목록에서 파스 트리와 구문 오류 복구   |
| ast      | 노드 정의, 파스 트리에서 AST 변환           |
| sema     | 이름 해석, 호출 그래프 순환 검사, 타입 검사 |
| optimize | AST 최적화와 HIR 최적화                     |
| eval     | 조성 해석, 시간 계산, 음역 검사로 HIR 생성  |
| lower    | HIR에서 LIR로 변환                          |
| diag     | Diagnostic 수집과 출력, 오류 코드 표        |
| tables   | 악기표, 온음계 표 같은 상수                 |
| rational | 유리수 연산                                 |

### 단계별 출력

각 단계의 결과는 "실행 규약" 절의 `--phase`와 `--emit`으로 본다. 테스트는 입력 파일과 기대 출력 파일의 쌍으로 작성하고, 실제 출력과 문자열로 비교한다.

## 의미 분석

의미 분석은 두 단계로 나뉜다. 4단계는 이름 해석, 타입 검사, 호출 그래프 순환 검사를 하고, 6단계(평가)는 조성 해석, 시간 계산, 음역 검사, 붙임줄 검사를 하면서 고수준 IR을 만든다. 이 절이 프로젝트의 중심이다.

### 4단계: 이름 해석과 타입 검사

다음 순서로 진행한다.

1. 헤더를 검사한다. 같은 종류의 헤더가 두 번 나오면 E102를 보고한다. `time`과 `unit`의 분자와 분모는 1 이상이고, `time`의 분모는 2의 거듭제곱이며, `tempo`는 4 이상 1000 이하여야 한다. 아니면 E105이다.
2. 모든 `def`를 먼저 전역 이름 공간에 등록한다(호이스팅). 이름이 중복되면 E103이다.
3. 각 `def` 본문에서 `Call` 노드를 모아 호출 그래프를 만들고, 깊이 우선 탐색으로 순환을 찾는다. 노드마다 미방문, 방문 중, 방문 완료 세 상태를 두고, 방문 중인 노드로 되돌아가는 간선을 발견하면 E401을 보고한다. 메시지에는 `f -> g -> f`처럼 순환 경로를 적는다.
4. 문장을 위에서 아래로 처리한다. `Assign`은 우변을 검사한 뒤 이름을 등록한다. `Def`는 매개변수 스코프를 만들어 본문을 검사하고 반환 타입과 비교한다. `Track`은 우변을 검사하고 악기 이름을 확인한다.
5. 이름을 찾을 때마다 `used`를 참으로 표시한다. 마지막에 `used`가 거짓인 정의는 W601, 트랙이 하나도 없으면 W602를 보고한다.

이름을 찾지 못하면 E101이다. 편집 거리가 2 이하인 이름이 있으면 `did you mean 'm1'?`처럼 제안을 붙인다.

### 6단계: 평가

평가는 타입이 맞는 AST를 실제 시간과 음높이를 가진 이벤트 열로 바꾼다. 평가 방식은 값 전달(call by value)이다. 변수는 정의할 때 평가해서 값을 저장하고, 함수 호출은 인자를 먼저 평가한 뒤 매개변수를 묶은 새 환경에서 본문을 평가한다. 함수 호출이 본문을 그 자리에 펼친 것과 같으므로 별도의 인라이닝 없이도 호출은 모두 사라진다.

```
PhraseVal   { events: [Event], length: Rational }
Event       = NoteEv { start, dur, pitch, tieNext, origin: Span }
            | RestEv { start, dur, origin: Span }
IntVal      { value }
IntervalVal { amount, kind }
```

`start`는 그 PhraseVal의 시작을 0으로 한 상대 시각이고, 모든 시간은 온음표를 1로 하는 Rational이다. `origin`은 이벤트를 만든 소스 위치이며 오류 보고에 쓴다.

| 노드      | 평가 결과                                                                                                                                   |
| --------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| NoteLit   | NoteEv 하나. start는 0, dur는 unit 곱하기 lenMul, pitch는 MIDI 번호로 변환한 값                                                             |
| RestLit   | RestEv 하나. dur는 unit 곱하기 lenMul                                                                                                       |
| Seq       | 항목을 순서대로 이어 붙인다. 각 항목의 start에 현재 오프셋을 더하고, 오프셋에 그 항목의 length를 더한다. BarMark에서는 마디 길이를 검사한다 |
| Par       | 두 구절의 이벤트를 같은 시작 시각에 합친다. length는 둘 중 큰 값이고, 두 값이 다르면 W603                                                   |
| Repeat    | count를 평가해 1 이상의 정수인지 확인하고(E402), 구절을 n번 이어 붙인다. 이벤트 수가 한도를 넘으면 E403                                     |
| Transpose | 음 이벤트의 pitch를 이동한다. 쉼표는 그대로 둔다                                                                                            |
| Group     | 내부 구절의 길이 T와 목표 길이 L(unit 곱하기 lenMul)로 비율 L / T를 구해 모든 start와 dur에 곱한다. length는 L                              |
| Call      | 인자를 평가한 뒤 새 환경에서 본문을 평가한다                                                                                                |
| Var       | 정의할 때 저장한 값을 쓴다. 값은 변경하지 않는다                                                                                            |
| Track     | 구절을 HIR 트랙으로 만들고 악기와 채널을 붙인 뒤 음역, 붙임줄, 트랙 길이를 검사한다                                                         |

MIDI 번호는 다음 식으로 계산한다. 이름별 기본값은 C=0, D=2, E=4, F=5, G=7, A=9, B=11이고 올림표는 +1, 내림표는 -1이다.

```
midi = 12 * (octave + 1) + base(letter) + accidental
```

검사 범위는 다음과 같다. `Assign` 문장은 트랙에서 쓰이지 않아도 모두 평가해서 오류를 보고한다. `Def`는 호출될 때만 평가하므로 호출되지 않은 함수의 시간, 음역 오류는 보고되지 않는다. 타입 오류는 4단계에서 호출 여부와 상관없이 보고된다.

### 조성에 따른 온음계 이조

이조 `+ Nd`는 조성의 음계 위에서 N계단 이동하는 연산이고, 음계에 없는 음에는 쓸 수 없다(E307). 그런 음은 반음 단위 이조를 쓴다. 반음 단위 이조 `+ Nst`는 조성과 무관하게 MIDI 번호에 N을 더한다. `-` 연산자는 N의 부호를 바꾼다.

```
MAJOR = [0, 2, 4, 5, 7, 9, 11]
MINOR = [0, 2, 3, 5, 7, 8, 10]        // 자연 단음계

diatonicShift(pitch, n, tonicPc, scale):
    o = (pitch - tonicPc) mod 12       // 으뜸음 기준 오프셋, 0 이상 11 이하
    if o not in scale: error E307      // 음계 밖의 음은 온음계 이조를 쓸 수 없다
    k    = scale 안에서 o의 위치         // 0 이상 6 이하
    base = pitch - o                   // pitch 이하에서 가장 가까운 으뜸음
    k2   = k + n
    oct  = floor(k2 / 7)               // 내림 나눗셈, 음수도 같은 규칙
    deg  = k2 - 7 * oct                // 0 이상 6 이하
    return base + 12 * oct + scale[deg]
```

`tonicPc`는 으뜸음의 음이름 번호이다(C는 0, G는 7, A는 9). 계산 예시는 다음과 같다.

| 조성   | 입력        | 계산                                    | 결과               |
| ------ | ----------- | --------------------------------------- | ------------------ |
| C 장조 | C4(60) + 2d | o=0, k=0, k2=2, scale\[2\]=4            | 64 (E4), 반음 4개  |
| C 장조 | D4(62) + 2d | o=2, k=1, k2=3, scale\[3\]=5            | 65 (F4), 반음 3개  |
| C 장조 | G4(67) + 2d | o=7, k=4, k2=6, scale\[6\]=11           | 71 (B4)            |
| C 장조 | C4(60) - 1d | k=0, k2=-1, oct=-1, deg=6               | 59 (B3)            |
| C 장조 | C4(60) + 7d | k2=7, oct=1, deg=0                      | 72 (C5), 한 옥타브 |
| G 장조 | B4(71) + 2d | tonicPc=7, o=4, k=2, k2=4               | 74 (D5)            |
| A 단조 | A4(69) + 2d | tonicPc=9, o=0, k=0, k2=2, MINOR\[2\]=3 | 72 (C5), 반음 3개  |

C 장조의 C4 + 2d(반음 4개)와 A 단조의 A4 + 2d(반음 3개)가 같은 `2d`로 다른 반음 수를 만드는 것이 조성 의존 이조의 예이다. 쉼표 이벤트는 이조해도 바뀌지 않는다.

### 시간 계산

모든 시간은 온음표를 1로 하는 Rational로 계산하고, 마지막에 정수 틱으로 바꿀 수 있는지만 검사한다. 부동소수점은 쓰지 않는다.

- 음의 길이는 `unit` 곱하기 `lenMul`이다. `unit`의 기본값은 1/4이다.
- 4분음표당 480틱(PPQ 480)이므로 온음표 하나는 1920틱이다. 틱 변환은 `ticks(r) = r.num * 1920 / r.den`이고, 나누어떨어지지 않으면 E302이다.
- 검사 대상은 평가 중 만들어지는 모든 `start`와 `dur`이다. 묶음 안에서 생긴 문제는 음마다 보고하지 않고 묶음 노드의 위치에 한 번만 보고한다.
- 마디 길이 M은 `timeNum / timeDen`이다. 4/4는 1, 3/4는 3/4, 6/8은 3/4, 5/4는 5/4이다.
- BAR 검사: 구절을 이루는 `Seq`에서 직전 BAR(처음에는 `Seq`의 시작)부터 이번 BAR까지의 길이가 M과 같아야 한다. 구간 길이가 0이면 검사하지 않는다(맨 앞 BAR, 연속한 BAR). 다르면 E301을 BAR 위치에 보고하고 모자라거나 넘치는 길이를 메시지에 적는다.
- 트랙 길이 검사: 트랙 전체 길이가 M의 정수배가 아니면 E301을 트랙 식의 시작 위치에 보고한다.
- BAR 검사는 그 `Seq`의 시작을 마디의 시작으로 본다. 변수나 함수 호출로 가져온 구절 안의 BAR는 그 구절을 만들 때 이미 검사했다.

시간 계산 예시는 다음과 같다(`unit 1/4`, `time 4/4`).

- `C4 E4 G4 E4`는 길이 1(4개 곱하기 1/4)이라 통과한다.
- BAR로 감싼 `C4 E4 G4`는 길이가 3/4라서 E301(1/4 부족)이다.
- `[C4 D4 E4]:1`은 세 음이 1/4을 나눠 가져 음마다 1/12 온음표, 즉 160틱이라 통과한다.
- `[C4 D4 E4 F4 G4 A4 B4]:1`은 음마다 1/28 온음표이고 1920 / 28이 정수가 아니므로 E302이다.
- `E4:/7`도 길이가 1/28이라 E302이다. `E4:/3`은 1/12이라 160틱이므로 통과한다.

### 음역과 악기표

악기 이름은 `tables` 모듈의 악기표에 있어야 한다. 아래 값은 초안이며 상수로 두어 바꿀 수 있게 한다.

| 이름   | 음역       | MIDI 번호   | GM 프로그램 |
| ------ | ---------- | ----------- | ----------- |
| piano  | A0 부터 C8 | 21 부터 108 | 0           |
| guitar | E2 부터 E6 | 40 부터 88  | 24          |
| bass   | E1 부터 G4 | 28 부터 67  | 32          |
| cello  | C2 부터 C6 | 36 부터 84  | 42          |
| violin | G3 부터 E7 | 55 부터 100 | 40          |
| flute  | C4 부터 C7 | 60 부터 96  | 73          |

- 트랙의 모든 NoteEv가 음역 안에 있는지 검사한다. 벗어나면 E303을 그 음의 `origin` 위치에 보고한다. 같은 `origin`에서 나온 이벤트(반복으로 생긴 사본)는 한 번만 보고한다.
- 채널은 트랙 선언 순서대로 0부터 번호를 붙이되 9번 채널(타악기)은 건너뛴다. 사용할 수 있는 채널은 0부터 8, 10부터 15까지 15개이고, 16번째 트랙을 선언하면 E305이다.

### 정적 평가

컴파일 시점에 모든 계산이 끝나도록 다음을 보장한다.

- 함수 재귀를 금지한다(4단계의 호출 그래프 순환 검사).
- 반복 횟수는 평가 결과가 1 이상의 정수여야 한다. 아니면 E402이다.
- 함수 호출이 64단계보다 깊어지면 E403이다.
- 평가 중 만들어진 이벤트의 총 수가 한도(기본 100000)를 넘으면 E403이다. 반복이 중첩되어 이벤트가 급증하는 입력을 막기 위한 규칙이다.
- Int 값은 리터럴, 이름, 호출 인자로만 만들어지고 산술 연산이 없다. 따라서 반복 횟수는 평가 시점에 항상 확정된다.

재귀가 없고 반복 횟수가 유한하므로 모든 프로그램의 평가가 유한한 시간에 끝난다.

### 붙임줄 검사

붙임줄 `~`는 같은 음높이의 다음 음과 이어진다는 뜻이다. 트랙의 이벤트를 모두 만든 뒤 다음 알고리즘으로 검사한다.

```
byStart = 트랙의 이벤트를 start 시각별로 묶은 맵
각 NoteEv e (e.tieNext 가 참):
    t = e.start + e.dur
    byStart[t] 안에 pitch 가 e.pitch 인 NoteEv 가 있으면 통과
    없으면 E304
```

실패 메시지는 원인을 구분한다. 다음 시각에 시작하는 음이 없는 경우, 쉼표인 경우, 다른 음높이인 경우이다. 병렬 구절 때문에 같은 시각에 여러 음이 있어도 같은 음높이가 하나라도 있으면 통과한다.

### 경고

- W601: 정의했지만 쓰지 않은 변수나 함수
- W602: `track`이 하나도 없는 프로그램
- W603: 병렬 `&`의 두 구절 길이가 다름(짧은 쪽 뒤는 비어 있는 것으로 본다)

경고는 컴파일을 중단하지 않는다.

## 중간 표현

중간 표현은 두 가지다. 고수준 IR(HIR)은 유리수 시간을 쓰고, 저수준 IR(LIR)은 정수 틱을 쓴다. LIR의 이벤트 하나가 MIDI 음 이벤트 하나에 대응한다.

### 고수준 IR (HIR)

6단계(평가)가 만들고 7단계(최적화)가 다듬는다. 이벤트의 시각은 트랙의 시작을 0으로 한 절대 시각이고, 모든 시간은 온음표를 1로 하는 Rational이다.

```
Hir      { header, tracks: [HirTrack] }
HirTrack { instrument, channel, events: [Event] }       // start 오름차순
Event    = NoteEv { start, dur, pitch, tieNext, origin }
         | RestEv { start, dur, origin }
```

### 저수준 IR (LIR)

8단계(하강)가 만든다. 시간이 정수 틱이고 쉼표와 붙임줄이 없다.

```
Lir      { ppq: 480, tempo, timeNum, timeDen, tonic, mode, tracks: [LirTrack] }
LirTrack { instrument, channel, events: [ (tick, channel, pitch, duration) ] }
```

### 하강 규칙

1. NoteEv 하나마다 이벤트 (ticks(start), channel, pitch, ticks(dur)) 하나를 만든다. 6단계에서 모든 시간이 정수 틱임을 이미 확인했으므로 하강은 실패하지 않는다.
2. RestEv는 버린다. 쉼표는 이벤트 사이의 빈 시간으로만 남는다.
3. 이벤트를 (tick, channel, pitch) 오름차순으로 정렬한다. 같은 입력의 출력이 항상 같아야 문자열 비교로 테스트할 수 있다.
4. 헤더 값은 그대로 복사한다.

### MIDI 대응

SMF 출력기는 선택 사항이다. 구현한다면 LIR을 다음 규칙으로 쓴다.

| LIR 요소                         | SMF 요소                                                                                                                           |
| -------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------- |
| ppq 480                          | 헤더 chunk의 division 480                                                                                                          |
| tempo T                          | Set Tempo 메타 이벤트, 4분음표당 마이크로초는 60000000 / T (T가 120이면 500000)                                                    |
| timeNum, timeDen                 | 박자표 메타 이벤트, 분모는 2의 거듭제곱 지수로 기록(분모 4는 2, 분모 8은 3). 분모가 2의 거듭제곱이 아니면 출력기가 지원하지 않는다 |
| 트랙의 instrument                | Program Change, 악기표의 GM 프로그램 번호                                                                                          |
| (tick, channel, pitch, duration) | tick에 Note On, tick + duration에 Note Off. 벨로시티는 80으로 고정                                                                 |

같은 틱의 이벤트는 Note Off를 Note On보다 먼저 쓴다. 조표 메타 이벤트는 쓰지 않아도 된다.

### 텍스트 출력 형식

골든 파일 테스트를 위해 `--emit hir`와 `--phase ir`의 출력 형식을 다음과 같이 고정한다.

```
// --emit hir
track piano channel 0
note 0 1/4 60
note 1/4 1/4 64
rest 1/2 1/4
note 3/4 1/4 64 tie

// --phase ir
ppq 480 tempo 120 time 4/4 key C major
track piano channel 0
0 0 60 480
480 0 64 480
```

HIR의 한 줄은 `note <start> <dur> <pitch>` 뒤에 붙임줄이면 `tie`가 오고, 쉼표는 `rest <start> <dur>`이다. LIR의 한 줄은 `tick channel pitch duration`이다.

### 예시: 프로그램 P의 HIR과 LIR

프로그램 P는 `time 4/4`, `key C`, `m1 = C4 E4 G4 E4`, `track piano = m1 m1+2d`이다. 두 번째 마디는 `m1`의 각 음을 C장조에서 두 계단 올린 것이라 C는 E로, E는 G로, G는 B로 바뀐다.

```
// HIR
track piano channel 0
note 0 1/4 60
note 1/4 1/4 64
note 1/2 1/4 67
note 3/4 1/4 64
note 1 1/4 64
note 5/4 1/4 67
note 3/2 1/4 71
note 7/4 1/4 67

// LIR
ppq 480 tempo 120 time 4/4 key C major
track piano channel 0
0 0 60 480
480 0 64 480
960 0 67 480
1440 0 64 480
1920 0 64 480
2400 0 67 480
2880 0 71 480
3360 0 67 480
```

## 최적화

최적화는 AST 단계의 규칙 두 가지(함수 인라이닝, 이조 접기)와 HIR 단계의 규칙 두 가지(붙임줄 병합, 쉼표 병합)로 이루어진다. 모든 규칙은 최종 LIR의 의미를 바꾸지 않는다. 즉 최적화를 켜든 끄든 LIR이 같아야 한다.

### 규칙 목록

| 규칙          | 단계    | 적용 조건                                                           | 변환                                                      |
| ------------- | ------- | ------------------------------------------------------------------- | --------------------------------------------------------- |
| 함수 인라이닝 | 5 (AST) | 항상. 재귀는 4단계에서 이미 금지됨                                  | Call 노드를 본문으로 치환하고 매개변수를 인자 식으로 바꿈 |
| 이조 접기     | 5 (AST) | 연속한 두 이조가 같은 종류(둘 다 d 또는 둘 다 st)이고 크기가 리터럴 | 부호를 반영한 합으로 이조 하나를 만듦                     |
| 붙임줄 병합   | 7 (HIR) | 항상(필수 변환)                                                     | 붙임줄로 이어진 음을 하나로 합침                          |
| 쉼표 병합     | 7 (HIR) | 서로 이어지는 쉼표                                                  | 하나로 합침                                               |

붙임줄 병합은 LIR에 붙임줄 정보가 없으므로 최적화 옵션과 상관없이 항상 수행한다. 나머지 세 규칙은 `-O0` 옵션으로 끌 수 있다.

### 함수 인라이닝

`Call(f, [a1, ..., an])`을 `f`의 본문에서 매개변수 `pi`를 `ai`로 치환한 식으로 바꾼다. 언어에 부수 효과가 없으므로 인자를 여러 번 복제해도 값이 같다. 인라이닝 결과의 노드 수가 한도(기본 100000)를 넘으면 E403을 보고한다. 변환 후에는 AST에 `Call` 노드가 남지 않는다.

```
// 변환 전
def twice(p: Phrase): Phrase = p p
track piano = twice(m1 + 2d)

// 변환 후 (--emit ast-opt)
Track(piano, Seq[Transpose(Var(m1), +2d), Transpose(Var(m1), +2d)])
```

### 이조 접기

`Transpose(Transpose(e, i1, s1), i2, s2)`에서 `i1`과 `i2`가 같은 종류의 리터럴이면 크기를 `s1 * a1 + s2 * a2`로 합쳐 `Transpose` 하나로 만든다. 합이 음수이면 부호를 -로 바꾸고 절댓값을 쓰고, 합이 0이면 `Transpose`를 없앤다. 종류가 다른 이조는 접지 않는다.

- `m1 + 2d + 3d`는 `m1 + 5d`가 된다.
- `m1 + 3st - 3st`는 `m1`이 된다.
- `m1 + 2d + 3st`는 그대로 둔다.

온음계 이조는 음계에 속한 음에서 계단 번호를 더하는 연산이다. 음계 밖의 음은 6단계가 거부하므로(E307) 두 번 이동한 결과와 합쳐서 한 번 이동한 결과가 같다. 반음 이동은 정수 덧셈이라 항상 성립한다.

### 붙임줄 병합

트랙의 이벤트에서 `tieNext`가 참인 음 e를 찾아, 시각 `e.start + e.dur`에 시작하는 같은 음높이의 음 n과 합친다. 합친 음의 `dur`는 둘을 더한 값이고 `tieNext`는 n의 값을 따른다. 체인이 길면 끝까지 따라가며 합친다. 짝이 있다는 것은 6단계의 붙임줄 검사(E304)가 보장하므로 이 단계에서 짝이 없는 경우는 없다.

```
// 변환 전 (--emit hir)
note 0 1/4 60 tie
note 1/4 1/4 60
note 1/2 1/2 64

// 변환 후 (--emit hir-opt)
note 0 1/2 60
note 1/2 1/2 64
```

### 쉼표 병합

앞 쉼표의 끝 시각이 뒤 쉼표의 시작 시각과 같으면 하나로 합친다. 쉼표는 하강에서 버려지므로 LIR 결과는 변하지 않고, `--emit hir-opt`로만 확인할 수 있다.

```
// 변환 전
rest 0 1/4
rest 1/4 1/4
note 1/2 1/2 60

// 변환 후
rest 0 1/2
note 1/2 1/2 60
```

### 적용 순서와 검증

인라이닝을 먼저 하고 이조 접기를 나중에 한다. 인라이닝 뒤에야 연속한 이조가 드러나는 경우가 있기 때문이다.

```
def up(p: Phrase): Phrase = p + 2d
track piano = up(m1) + 3d
```

이 프로그램은 인라이닝으로 `(m1 + 2d) + 3d`가 되고, 이조 접기로 `m1 + 5d`가 된다.

검증 방법은 다음과 같다. 모든 테스트 프로그램에 대해 `-O0`으로 만든 LIR과 기본 옵션으로 만든 LIR이 같은지 비교한다. 같지 않으면 최적화 규칙에 오류가 있는 것이다.

## 오류 처리

모든 단계는 공통 진단 모듈(diag)로 오류와 경고를 보고하고, 한 번의 실행에서 가능한 한 많은 오류를 정확한 위치와 함께 보여 주는 것을 목표로 한다.

### 출력 형식

진단 하나는 한 줄이다. 줄과 열은 1부터 센다. 제안이 있으면 같은 줄 끝에 괄호로 붙인다.

```
<파일>:<줄>:<열>: error[<코드>]: <메시지> (<제안>)
```

```
example.clef:1:18: error[E201]: operator '+' is not defined for (Note, Note) (expected (Note + Interval) or (Phrase + Interval))
```

- 오류가 하나라도 있으면 종료 코드 2를 반환하고 단계의 결과를 출력하지 않는다. 경고만 있으면 종료 코드 0이다.
- 모든 진단은 출력 전에 (줄, 열) 오름차순으로 정렬한다. 같은 입력의 출력이 항상 같아야 테스트할 수 있다.
- 진단(오류와 경고)은 정렬한 뒤 앞의 50개까지만 출력하고, 넘치면 마지막 줄에 `too many errors`를 출력한다.
- 코드의 목록은 `docs/errors.md`에 싣는다. 그 문서의 모든 코드에는 그 코드를 내는 예제 프로그램이 있어야 하고, 테스트가 이를 확인한다.

### 오류 코드표

### 메시지 작성 규칙

- 메시지의 첫 부분은 무엇이 잘못됐는지, 괄호 안의 제안은 어떻게 고치는지를 쓴다.
- 길이는 분수로 쓴다(3/4). 음은 소스에 쓴 그대로 쓴다(C4).
- 이름 오류(E101, E104)에는 편집 거리가 2 이하이고 가장 가까운 이름 하나를 `did you mean 'm1'?` 형태로 제안한다.
- 타입 오류가 난 식을 피연산자로 가진 식은 오류를 다시 보고하지 않는다.

### 복구 전략

| 단계                 | 복구 방법                                                                                                                                               |
| -------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 렉서                 | 오류가 난 문자나 토큰을 버리고 다음 문자부터 계속 읽는다                                                                                                |
| 파서                 | 문장 단위로 동기화한다. 문장 안에서 오류가 나면 괄호 깊이가 0인 첫 NEWLINE까지 토큰을 버리고 다음 문장부터 다시 파싱한다. 오류가 난 문장은 AST에서 뺀다 |
| 이름 해석, 타입 검사 | 오류가 난 식의 타입을 오류 타입으로 둔다. 정의에 실패한 이름도 오류 타입으로 등록해 이후의 사용에서 E101이 반복되지 않게 한다                           |
| 평가                 | 오류가 난 정의는 건너뛰고 다음 정의를 계속 평가한다. 오류가 난 정의를 쓰는 식은 조용히 건너뛴다                                                         |

요청한 단계까지 가는 도중에 오류가 있으면 진단만 출력한다. `--phase`보다 뒤 단계의 오류는 보고하지 않는다. 예를 들어 타입 오류만 있는 파일은 `--phase parse`에서 성공한다.

## 테스트 명세

각 단계는 입력과 기대 출력을 쌍으로 고정해 단계별로 검증한다. 진단 예시의 파일 이름은 `t.clef`이다. 아래 예시는 모두 `time 4/4`, `key C`, `unit 1/4`, `tempo 120`이 기본값이라고 가정한다. 예시 안의 줄 번호와 열 번호는 1부터 센다. 진단의 정렬 순서는 줄, 열, 코드 순이다.

공통 프로그램 P는 다음과 같다.

```
time 4/4
key C

m1 = C4 E4 G4 E4
track piano = m1 m1+2d
```

### 1단계: 렉서 (`--phase lex`)

토큰 하나를 `<줄>:<열> <종류> <원문>` 한 줄로 낸다. NEWLINE의 원문은 `\n`으로 적고 EOF는 출력하지 않는다.

```
# 입력
m1 = C#4 c4 E4:2~ |
# 기대 출력
1:1 IDENT m1
1:4 EQ =
1:6 NOTE C#4
1:10 IDENT c4
1:13 NOTE E4
1:15 COLON :
1:16 INT 2
1:17 TIE ~
1:19 BAR |
1:20 NEWLINE \n

# 입력
time 4/4
# 기대 출력
1:1 KW_TIME time
1:6 INT 4
1:7 SLASH /
1:8 INT 4
1:9 NEWLINE \n

# 입력
m1+2d
# 기대 출력
1:1 IDENT m1
1:3 PLUS +
1:4 INTERVAL 2d
1:6 NEWLINE \n

# 입력
key C minor
# 기대 출력
1:1 KW_KEY key
1:5 PITCHCLASS C
1:7 KW_MINOR minor
1:12 NEWLINE \n

# 입력
m1 = C10
# 기대 출력
t.clef:1:6: error[E002]: invalid note 'C10': the octave must be a single digit

# 입력
m1 = 2x
# 기대 출력
t.clef:1:6: error[E003]: invalid interval '2x': use d (scale steps) or st (semitones)

# 입력
m1 = ?
# 기대 출력
t.clef:1:6: error[E001]: unexpected character '?'

# 입력 (빈 파일)
# 기대 출력
t.clef:1:1: error[E005]: this is not a valid program: the file is empty
```

### 2단계: 파서 (`--phase parse`)

```
# 입력
track piano = m1 m1+2d
# 기대 출력 (파스 트리)
TrackStmt
+- IDENT piano
+- Par
   +- Seq
      +- Item -> Post -> Atom -> IDENT m1
      +- Item -> Post
         +- Post -> Atom -> IDENT m1
         +- PLUS
         +- Atom -> INTERVAL 2d

# 입력
track a = m1 +
track b = * 2
# 기대 출력
t.clef:1:15: error[E010]: expected expression after '+'
t.clef:2:11: error[E010]: expected expression, found '*'

# 입력
m1 = (C4 E4
# 기대 출력
t.clef:1:6: error[E011]: unclosed '('

# 입력
m1 = C4 E
# 기대 출력
t.clef:1:9: error[E002]: note 'E' needs an octave (for example E4)

# 입력
m1 = C4
time 3/4
# 기대 출력
t.clef:2:1: error[E010]: unexpected 'time', headers must come before statements
```

첫 번째 오류 예시처럼 한 문장에서 오류가 나도 다음 줄부터 다시 파싱하므로 두 오류가 모두 보고되어야 한다.

### 3단계: AST (`--emit ast`)

```
# 입력
track piano = m1 m1+2d
# 기대 출력
Track(piano, Seq[Var(m1), Transpose(Var(m1), +2d)])

# 입력
m1 = | C4 E4 |
# 기대 출력
Assign(m1, Seq[Bar, Note(C4), Note(E4), Bar])

# 입력
m1 = [C4 D4 E4]:1
# 기대 출력
Assign(m1, Group(Seq[Note(C4), Note(D4), Note(E4)], 1))

# 입력
m1 = C4:/2 C4:3/2
# 기대 출력
Assign(m1, Seq[Note(C4, 1/2), Note(C4, 3/2)])

# 입력
m1 = a+2d*2
# 기대 출력
Assign(m1, Repeat(Transpose(Var(a), +2d), 2))

# 입력
m1 = a b & c d
# 기대 출력
Assign(m1, Par(Seq[Var(a), Var(b)], Seq[Var(c), Var(d)]))
```

AST에는 괄호와 중간 규칙 노드가 없고, 공백 연결은 평탄한 `Seq`이다.

### 4단계: 이름 해석과 타입 검사 (`--phase sema`)

아래 기대 출력은 진단을 정렬한 순서로 적었다. 경고가 같이 나오는 입력은 경고를 함께 적었다.

```
# 입력: 프로그램 P
# 기대 출력
m1 : Phrase
track piano : Phrase

# 입력
m1 = C4:4
track piano = m2
# 기대 출력
t.clef:1:1: warning[W601]: 'm1' is defined but never used
t.clef:2:15: error[E101]: undefined name 'm2' (did you mean 'm1'?)

# 입력
time 4/4
time 3/4
track piano = C4:4
# 기대 출력
t.clef:2:1: error[E102]: duplicate header 'time'

# 입력
m1 = C4:4
m1 = D4:4
track piano = m1
# 기대 출력
t.clef:2:1: error[E103]: 'm1' is already defined at line 1

# 입력
track pino = C4:4
# 기대 출력
t.clef:1:7: error[E104]: unknown instrument 'pino' (did you mean 'piano'?)

# 입력
track piano = C4 + C4
# 기대 출력
t.clef:1:18: error[E201]: operator '+' is not defined for (Note, Note) (expected (Note + Interval) or (Phrase + Interval))

# 입력
track piano = C4 2d
# 기대 출력
t.clef:1:18: error[E201]: sequence items must be Note or Phrase, found Interval

# 입력

# 기대 출력
t.clef:2:15: error[E203]: 'up' expects 2 arguments, found 1

# 입력

# 기대 출력
```

### 6단계: 평가 (`--emit hir`)

평가 단계의 오류 예시다. 오류가 난 정의를 쓰는 식은 조용히 건너뛰므로 아래에 적은 진단만 나온다.

```

# 기대 출력

# 입력

# 기대 출력
```

### 8단계: 저수준 IR (`--phase ir`)

프로그램 P의 HIR과 LIR은 중간 표현 절의 예시와 같다. 출력의 첫 줄은 항상 헤더 줄이다. 아래 예시에서는 기본값 헤더 줄 `ppq 480 tempo 120 time 4/4 key C major`를 생략했고, 헤더가 다른 입력에만 헤더를 적었다.

```
# 입력: 묶음(셋잇단음표)
track piano = [C4 D4 E4]:1 G4:3
# 기대 출력
track piano channel 0
0 0 60 160
160 0 62 160
320 0 64 160
480 0 67 1440

# 입력: 병렬
track piano = (C4 E4 G4 C5) & C3:4
# 기대 출력
track piano channel 0
0 0 48 1920
0 0 60 480
480 0 64 480
960 0 67 480
1440 0 72 480

# 입력: 쉼표
track piano = C4 _ E4:2
# 기대 출력
track piano channel 0
0 0 60 480
960 0 64 960

# 입력: 반복
track piano = (C4 E4)*2
# 기대 출력
track piano channel 0
0 0 60 480
480 0 64 480
960 0 60 480
1440 0 64 480

# 입력: 트랙 두 개는 채널이 다르다
track piano = C4:4
track bass = C2:4
# 기대 출력
track piano channel 0
0 0 60 1920
track bass channel 1
0 1 36 1920

# 입력: 함수 호출
def up(p: Phrase, i: Interval): Phrase = p + i
track piano = up(C4:4, 2d)
# 기대 출력
track piano channel 0
0 0 64 1920

# 입력: 반음 단위 이조

# 기대 출력
```

마지막 두 예시는 같은 `+ 2d`가 조성에 따라 다른 반음 수(G 장조에서 B4는 반음 3개, A 단조에서 A4는 반음 3개)를 만드는 것을 확인한다. C 장조의 `C4 + 2d`는 반음 4개이다.

### 5단계와 7단계: 최적화

```
# 입력: 인라이닝 (--emit ast-opt)
def twice(p: Phrase): Phrase = p p
m1 = C4 E4
track piano = twice(m1 + 2d)
# 기대 출력
Assign(m1, Seq[Note(C4), Note(E4)])
Track(piano, Seq[Transpose(Var(m1), +2d), Transpose(Var(m1), +2d)])

# 입력: 같은 종류의 이조 접기 (--emit ast-opt)
m1 = C4 E4 G4 E4
track piano = m1 + 2d + 3d
# 기대 출력
Assign(m1, Seq[Note(C4), Note(E4), Note(G4), Note(E4)])
Track(piano, Transpose(Var(m1), +5d))

# 입력: 부호가 다른 반음 이조 (--emit ast-opt)
m1 = C4 E4 G4 E4
track piano = m1 + 3st - 3st
# 기대 출력
Assign(m1, Seq[Note(C4), Note(E4), Note(G4), Note(E4)])
Track(piano, Var(m1))

# 입력: 종류가 다른 이조는 접지 않는다 (--emit ast-opt)
m1 = C4 E4 G4 E4
track piano = m1 + 2d + 3st
# 기대 출력
Assign(m1, Seq[Note(C4), Note(E4), Note(G4), Note(E4)])
Track(piano, Transpose(Transpose(Var(m1), +2d), +3st))

# 입력: 인라이닝 뒤에 이조 접기 (--emit ast-opt)
def up(p: Phrase): Phrase = p + 2d
m1 = C4 E4 G4 E4
track piano = up(m1) + 3d
# 기대 출력
Assign(m1, Seq[Note(C4), Note(E4), Note(G4), Note(E4)])
Track(piano, Transpose(Var(m1), +5d))

# 입력: 붙임줄 병합
track piano = C4~ C4 E4:2
# 기대 출력 (--emit hir)
track piano channel 0
note 0 1/4 60 tie
note 1/4 1/4 60
note 1/2 1/2 64
# 기대 출력 (--emit hir-opt)
track piano channel 0
note 0 1/2 60
note 1/2 1/2 64
# 기대 출력 (--phase ir)
track piano channel 0
0 0 60 960
960 0 64 960

# 입력: 쉼표 병합
track piano = _ _ C4:2
# 기대 출력 (--emit hir)
track piano channel 0
rest 0 1/4
rest 1/4 1/4
note 1/2 1/2 60
# 기대 출력 (--emit hir-opt)
track piano channel 0
rest 0 1/2
note 1/2 1/2 60
# 기대 출력 (--phase ir)
track piano channel 0
960 0 60 960
```

### 성질 테스트

개별 입력만으로는 잡기 어려운 오류를 잡기 위해 모든 테스트 입력에 다음을 함께 검사한다.

- 최적화 무관: `-O0`으로 만든 LIR과 기본 옵션으로 만든 LIR이 같다.
- 결정성: 같은 입력을 두 번 실행해 출력이 같다.
- 정렬: LIR의 이벤트가 (tick, channel, pitch) 오름차순이다.
- 길이: 트랙의 모든 이벤트에서 `tick + duration`의 최댓값이 트랙 길이를 틱으로 바꾼 값 이하이다.
- 소리 보존: 붙임줄 병합 전 HIR에서 같은 음높이로 이어진 구간의 합집합과 LIR의 같은 음높이 구간의 합집합이 같다.

## 확인 사항

### 정해진 것

- 필수 범위는 lex, parse, sema, ir 네 단계이다. IR은 트리의 이름만 바꾼 것이면 인정되지 않는다. 실행되는 back end는 선택이고 가산점이 있을 수 있다.

### 확인할 것

- [ ] 데모는 팀원 두 사람이 모두 말해야 한다. 팀 구성을 확인한다.
- [ ] Conform 자동 채점이 어느 컴퓨터에서 `run.sh`를 실행하는가. 채점자의 컴퓨터라면 `vpx` 설치를 전제할 수 없다.

### 설계 결정 (임시 값)

아래 값은 구현을 시작하기 위해 정한 임시 값이며 구현하면서 바꿀 수 있다.

- 언어 이름은 Clef, 구현 언어는 TypeScript로 정했다.
- 조성은 장조와 자연 단음계만 지원하고, 곡 중간에 조성을 바꾸는 기능은 없다.
- 온음계 이조는 조성의 음계 안에 있는 음에만 허용한다(E307). 음계 밖의 음은 반음 이조를 쓴다.
- 못갖춘마디는 지원하지 않는다.
- 마디 검사는 BAR가 속한 구절의 시작을 기준으로 하는 지역 검사다.
- 악기표의 음역과 GM 프로그램 번호는 초안 값이다.
- 전개 한도는 이벤트 100000개이고, 벨로시티는 80으로 고정하며 다이내믹은 없다.
- 채널 9번(타악기)은 쓰지 않으므로 트랙은 최대 15개다.
- 박자표 분모는 SMF 출력을 위해 2의 거듭제곱만 지원한다.

### 데모

Zoom으로 10분이고 코드 설명은 GitHub 저장소 화면으로 한다. 시작 전에 터미널, GitHub, `docs` 폴더를 열어 두고, 데모 중에는 아무것도 설치하지 않는다. 되지 않는 기능이 있으면 시작할 때 먼저 말한다.

| 시간(분) | 하는 일                                                                                                                  |
| -------- | ------------------------------------------------------------------------------------------------------------------------ |
| 0 ~ 1    | 언어의 목적과 작은 프로그램 하나                                                                                         |
| 1 ~ 2    | `--phase lex`                                                                                                            |
| 2 ~ 4    | `--phase parse`. `m1+2d*2`와 `a b & c d`로 우선순위를 보인다                                                             |
| 4 ~ 6    | `docs/errors.md`를 보인 뒤 오류 프로그램 3개                                                                             |
| 6 ~ 8    | `--phase ir`. 한 줄을 설명하고, 트리에 없는 일(함수 인라이닝, 온음계 이조 계산, 정수 틱 변환, 붙임줄 병합)을 하나 말한다 |
| 8 ~ 9    | 현장에서 받은 테스트 실행                                                                                                |
| 9 ~ 10   | 코드와 AI 사용에 대한 질문. 팀원마다 따로 답한다                                                                         |

- 단계마다 쉬움, 중간, 오류 테스트를 하나씩 `examples/demo/<단계>/`에 둔다. 현장에서 처음 보는 테스트가 2개 더 온다.
- `docs/AI_USAGE.md`는 한 쪽이고 다섯 항목이다. 사용한 AI 도구와 단계, AI가 도움이 된 예, AI가 틀린 예와 대응, 테스트 방법(직접 쓴 것과 생성한 것), 줄 단위로 설명할 수 있는 파일 2개. 실제 경험을 팀원이 직접 쓴다.
- 예상 질문은 "이름이 선언됐는지 검사하는 파일 설명", "키워드를 하나 더할 때 고치는 파일과 순서", "AI가 틀리게 쓴 부분"이다.
- SMF 출력기를 구현했으면 마지막에 `.mid`를 만들어 재생한다. 곡은 저작권이 소멸한 파헬벨의 카논이다.
